# CLAUDE.md

## What this is

**Mizrahitality Simple** — a monorepo with two cooperating, **server-side-rendered** products (job-interview deliverable; keep everything **as simple as possible**):

- **Builder app** — owner-facing drag-and-drop website builder for non-technical hospitality venue owners; lets them sign up, create a site by naming the venue (slug derived from the name), build a **single page** (pinned venue-name header + repeatable Rich Text blocks, at most one Image, at most one Book Now button), publish, and view an analytics dashboard. Exposes a REST/JSON API.
- **Customer app** — public visitor site routed at `localhost:<port>/<slug>`; on each request it calls the Builder API for the published page (per slug), renders it server-side, and posts analytics events back.

The two apps communicate **only** over the documented REST API.

## Tech stack

- **Customer app:** Next.js (App Router, SSR) — public visitor site on port **5112** (`CUSTOMER_PORT`), routes at `localhost:5112/<slug>`. Reads the Builder API via `BUILDER_API_URL` (default `http://localhost:5111`).
- **Builder app:** Next.js (App Router) — owner-facing app on port **5111** (`BUILDER_PORT`); hosts the REST API under `app/api/`.
- **UI:** **shadcn/ui** (with its lucide-react icons) + **Tailwind v4** (CSS-first: `@import "tailwindcss"` + `@theme`; `@tailwindcss/postcss` plugin; no `tailwind.config.js`). No design files are provided up front — build clean, simple UI directly; a frontend design will be supplied later.
- **Drag-and-drop:** `@dnd-kit/core` + `@dnd-kit/sortable` (Builder canvas) — not hand-rolled.
- **Rich text:** **Tiptap** (bold/italic/headings/bullet+numbered lists/links); stored as sanitized HTML, rendered server-side on the Customer app.
- **Auth:** bcrypt-hashed passwords + a signed httpOnly session cookie — **no NextAuth** or other auth framework. The Builder↔Customer REST API itself has no auth.
- **Monorepo:** plain **pnpm workspace** (no Turborepo/Nx) — `apps/*` + `packages/*`, one lockfile, pnpm pinned via `packageManager`/`engines`.
- **Database:** **Prisma + SQLite** (file-based, Prisma's bundled SQLite — no `better-sqlite3`). DB file `apps/builder/prisma/dev.db`; `DATABASE_URL=file:./dev.db` (resolved relative to `prisma/schema.prisma`). All schema changes go through the `update-database` skill (logged in `apps/builder/prisma/CHANGELOG.md`).
- **Image storage:** uploaded images in a local **gitignored** dir `apps/builder/uploads/`, served via a Builder route handler at `GET /uploads/<file>`; plus a small **committed** stock-image set under `apps/builder/public/stock/`.
- **Tests:** Vitest, per-workspace config; moderate rigor — core logic (auth, analytics aggregation, REST contract) well-tested, lighter on the supplied UI; smoke tests are DB-independent.

## Hard constraints (apply everywhere)

- **SSR is mandatory** for the Customer app's published page; the Builder's framework must support SSR.
- The Customer app **is Next.js**; both apps are Next.js.
- It is a **monorepo** with shared API-contract types.
- **No UI design files (yet).** Use **shadcn/ui** components (and its lucide-react icons) for buttons and icons across both apps; build the rest as clean, simple UI. No bespoke design system.
- The REST API between the two apps has **no auth** (local demo); the **slug** (derived from the venue name) selects the site.

## Layout

Scaffolded by feature 1 (`monorepo-foundation`). pnpm workspace — `pnpm-workspace.yaml` globs `apps/*` + `packages/*`; one lockfile; pnpm pinned via `packageManager` (`pnpm@9.x`) / `engines` (`node >=20`). Root `package.json` scripts: `dev` (both apps via `concurrently`), `build` / `lint` / `typecheck` / `test` (each `pnpm -r --if-present run …`), `format` (Prettier), `db:migrate`, `seed`.

- `apps/builder/` — Builder app (Next.js App Router, port 5111). `app/` has the root layout, `page.tsx` (redirects by auth state: signed in → `/dashboard`, else → `/sign-in`), a public `(auth)/` route group (`layout.tsx` bounces already-signed-in visitors to `/dashboard`; `sign-in/` and `sign-up/` — shadcn `Card` pages with `useActionState` client forms), a gated `(owner)/` route group (`layout.tsx` calls `requireOwner()` + a header showing the owner email and a server-action sign-out button; `dashboard/page.tsx` shows the owner email + an "Open the site builder" link — analytics dashboard lands in `analytics-dashboard`; `builder/page.tsx` is the site builder — Server Component: `requireOwner()` → `getOwnerSite()`; no site → `create-site-form.tsx` (`"use client"`, `useActionState(createSiteAction)`, live slug hint); site exists → a frozen-slug banner (`http://localhost:5112/<slug>`) + `<SiteBuilder>`), an `app/uploads/[file]/route.ts` `GET` handler that streams owner-uploaded images from `uploads/` (filename-validated, path-traversal-guarded, immutable cache header; no auth); `app/api/` will hold the REST API. `lib/db.ts` is the Prisma client singleton; `lib/auth/` has the owner-auth modules — `password.ts` (bcryptjs hash/verify + a decoy hash), `session.ts` (pure HMAC-SHA256 signed-token sign/verify, `SESSION_COOKIE_NAME = "miz_session"`, 30-day max-age), `cookie.ts` (Next 15 async `cookies()` helpers — set/clear only callable from Server Actions), `validation.ts` (email/password validation + normalize), `accounts.ts` (`registerOwner`/`authenticateOwner` over an injectable `AuthDb`; the real `prisma` is lazy-`import()`-ed so unit tests stay DB-free), `current-owner.ts` (`getCurrentOwner` (`cache()`-wrapped) / `requireOwner` → `redirect("/sign-in")`), `actions.ts` (`"use server"` — `signUpAction`/`signInAction`/`signOutAction`); `lib/site/` has the site-builder modules — `types.ts` (the `Block` union `rich-text` | `image` | `book-now`, `PageContent = { blocks }`, `BLOCK_TYPES`, `SINGLETON_BLOCK_TYPES`, `SitePayload`, `BuilderSite`; `imageUrl` is relative — `/uploads/<uuid>.<ext>` or `/stock/<name>.svg` — features 5/8 resolve it absolutely), `slug.ts` (pure: `VENUE_NAME_RE = /^[A-Za-z ]+$/`, `slugifyVenueName` = spaces removed + lowercased, `validateVenueName`), `content.ts` (pure: `parsePageContent` — tolerant reader for `Site.contentJson`, drops invalid blocks, de-dups the singletons; `isValidBlock`, `validateBlocks` — at-most-one Image/Book Now; `countByType`), `sanitize.ts` (`sanitizeRichTextHtml` over `sanitize-html` — server-only allowlist; strips `<script>`/`on*`/`style`/`javascript:`/`<iframe>`/`<img>`, links get `rel="noopener noreferrer"`), `uploads-dir.ts` (`UPLOADS_DIR = path.join(process.cwd(), "uploads")`), `site.ts` (`getOwnerSite`/`slugExists`/`createSite` — Prisma helpers; `createSite` is DB-injectable via `CreateSiteDeps` and the real `prisma` is lazy-`import()`-ed, so unit tests stay DB-free), `actions.ts` (`"use server"` — `createSiteAction` (`useActionState`; collision → "that venue name is taken"; on ok `revalidatePath`+`redirect("/builder")`), `saveSiteAction` (re-auth + ownership re-check + validate name + parse/validate/sanitize blocks + `prisma.site.update` — name updates the display, slug stays frozen; Publish is feature 5, `isDraft` inert), `uploadImageAction` (re-auth + mime/size check + write `<uuid>.<ext>` to `uploads/` → `/uploads/<file>`)); `lib/utils.ts` is shadcn's `cn`; `lib/stock.ts` lists the bundled stock images. `components/ui/` holds shadcn components (`button`, `input`, `label`, `card`, `dialog`, `tooltip`, `separator`); `components.json` configures `shadcn add` (note: several pull in the unified `radix-ui` package). `components/site/` has the builder UI (all `"use client"` except `block-view`): `site-builder.tsx` (`@dnd-kit/core` `DndContext` + tray + canvas (pinned venue-name `<h1>` edited in place + `SortableContext` over the blocks) + live preview + a Save button via `useTransition` — no Publish), `block-tray.tsx` ("Drag into site" — 3 `useDraggable` items; Image/Book Now grey out once placed (`aria-disabled` + dimmed, not draggable) and the greyed Book Now shows "Only one is allowed." in a `Tooltip`), `sortable-block.tsx` (`useSortable` wrapper — grip handle + trash + dispatches to the type editor), `rich-text-editor.tsx` (**Tiptap v3** — `StarterKit.configure({ link: … })` (StarterKit v3 bundles Link), `immediatelyRender:false` for SSR, `shouldRerenderOnTransaction:true`, bold/italic/H1–H3/bullet+numbered lists/links toolbar; - `apps/customer/` — Customer app (Next.js App Router, SSR, port 5112). `app/[slug]/page.tsx` (the public per-venue Server Component) lands in the `customer-site` feature; for now `app/` has the root layout + a placeholder home page. `lib/env.ts` reads `BUILDER_API_URL` (default `http://localhost:5111`) and exports a configured `apiClient`. ## Build / run / test

First-time setup: `pnpm install` → `cp apps/builder/.env.example apps/builder/.env` and `cp apps/customer/.env.example apps/customer/.env` → `pnpm db:migrate` (`prisma migrate deploy` in `apps/builder`; idempotent; creates `apps/builder/prisma/dev.db`). Then:

- `pnpm dev` — both apps via `concurrently` (Builder http://localhost:5111, Customer http://localhost:5112). Override ports with `BUILDER_PORT` / `CUSTOMER_PORT`.
- `pnpm build` / `pnpm lint` / `pnpm typecheck` / `pnpm test` — across all workspaces (`pnpm -r --if-present run …`).
- `pnpm format` — Prettier write. `pnpm db:migrate` — apply migrations (idempotent; schema changes go through the `update-database` skill, logged in `apps/builder/prisma/CHANGELOG.md`). `pnpm seed` — no-op stub until the `demo-seed` feature.
- Per-app / per-package: `pnpm -F builder <script>` / `pnpm -F customer <script>` / `pnpm -F @mizrahitality/contracts <script>`. A single test file: `pnpm -F <name> exec vitest run <path>`.
